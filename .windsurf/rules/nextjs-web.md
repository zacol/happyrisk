# Next.js Web — Conventions & Patterns

## ⚠️ Read First — This Is Not the Next.js You Know

This project uses **Next.js 16** with **React 19**. APIs, conventions, and file structure may differ from your training data. Before writing any Next.js-specific code, check `node_modules/next/dist/docs/` for the authoritative reference. Read all deprecation notices.

## App Router

- Use the **App Router** exclusively. The `pages/` directory does not exist in this project.
- File conventions: `page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`, `not-found.tsx`.
- Route groups use the `(group)` naming convention (parentheses).
- All pages and layouts are **Server Components by default**. Add `'use client'` only when you need browser APIs, event handlers, or React hooks.

## Path Aliases

- Use the `@/` alias (maps to `src/`) for all internal imports. Never use `..` to traverse up directories.
- Import workspace packages via their package names: `@happyrisk/core/schemas`, `@happyrisk/core/types`, `@happyrisk/core/constants`.

## Data Fetching — TanStack Query

- Use **TanStack Query v5** (`@tanstack/react-query`) for **all server state** management.
- Never perform raw `fetch` or `axios` calls directly inside React components.
- Define query and mutation functions in `src/hooks/` or `src/lib/`.
- API calls go through the Axios instance configured in `src/lib/` — do not create ad-hoc Axios instances.
- Use `@tanstack/eslint-plugin-query` rules to keep query usage correct (already enforced by ESLint config).

## UI Components & Styling

- Use **shadcn/ui** components (backed by `@base-ui/react`) as the primary component library. Do not install competing headless UI libraries.
- Use **Lucide React** for all icons. Do not import from other icon libraries.
- Use **TailwindCSS v4** for all styling. Do not write inline styles or plain CSS (except in `globals.css` for design tokens).
- Use **`tailwind-merge`** (`twMerge` / `cn`) to merge conditional Tailwind classes.
- Use **`class-variance-authority`** (CVA) for variant-based component styling.
- Use **`next-themes`** for dark/light mode. Never hard-code color values that break in alternate themes.
- Use **Sonner** for toast notifications. Do not use `alert()` or other browser dialogs.

## Authentication

- Auth tokens are stored **exclusively in `HttpOnly` cookies** set by the NestJS backend. Never store tokens in `localStorage`, `sessionStorage`, or React state.
- The `proxy.ts` middleware handles silent token rotation (access token expired → refresh → retry). No auth logic belongs inside page components.
- Protected routes are defined by the `matcher` in `proxy.ts`. All new protected routes must fall under the matcher pattern.
- To read the current user, call `GET /api/auth/me`. Do not decode or verify JWTs on the frontend for security decisions — only for UX (e.g., role-based rendering).
- For route protection logic, check `proxy.ts` — not inside layouts or pages.

## API Communication

- All requests to the NestJS API use the base URL from `process.env.NEXT_PUBLIC_API_URL`.
- Cookies are forwarded automatically by the browser (credentials: `include`). Do not manually attach tokens to headers.
- Handle `401 Unauthorized` globally via an Axios interceptor or TanStack Query's `onError` — redirect to `/login`.

## Environment Variables

- Public variables (accessible in browser) must be prefixed with `NEXT_PUBLIC_`.
- Required variables must throw at startup if missing — never fall back silently in production.
- Keep `.env.example` up to date with every new variable added.

## Component Organization

```
src/
  app/           # App Router routes (layouts, pages, loading, error)
  components/
    ui/          # Generic shadcn/ui primitives (generated by shadcn CLI)
    <feature>/   # Feature-specific components (e.g., risk-registry/, surveys/)
  hooks/         # Custom React hooks + TanStack Query hooks
  lib/           # API clients, utilities, providers
```

- Keep components small and focused — under ~150 lines. If a component exceeds this, decompose it.
- Extract reusable logic into custom hooks in `src/hooks/`.
- Providers (QueryClient, ThemeProvider, etc.) are wrapped in `src/lib/providers.tsx` and mounted once in the root layout.

## Component Principles

- **Composition over complexity** — Build complex UIs by composing small, focused components. Each component has a single, clear responsibility. Prefer `children`, slots, and compound patterns over deeply nested prop trees.
- **Declarative over imperative** — Define what the UI should look like based on state. Let React handle reconciliation. Never manipulate the DOM directly.
- **Design tokens only** — All visual values (colors, spacing, typography, shadows, radii) must come from TailwindCSS theme tokens or CSS custom properties in `globals.css`. Never hardcode raw values like `#3B82F6` or `16px` in component code.
- **If context is missing, ask** — If design specs, tokens, or requirements are unclear, stop and ask. Do not guess visual implementation.

## Component Composition Patterns

| Pattern             | Implementation                                                           | When to use                                    |
| ------------------- | ------------------------------------------------------------------------ | ---------------------------------------------- |
| Content projection  | `children` prop                                                          | Single content slot (cards, wrappers, layouts) |
| Slots               | Named `ReactNode` props: `header`, `footer`, `sidebar`                   | Multiple projection points                     |
| Compound components | Shared context between parent + sub-components (`Tabs` + `Tabs.Content`) | Tightly coupled UI groups (tabs, accordion)    |
| Render delegation   | Render props: `renderItem={(item) => <Item data={item} />}`              | When consumer controls rendering of items      |

- Prefer `children` for single content projection — it's the simplest pattern.
- Use named `ReactNode` props (slots) when a component needs multiple insertion points.
- Use compound components for tightly coupled UI groups where sub-components share implicit state.
- If a component accepts more than **~7 props**, it likely needs decomposition into composed sub-components.

## Component Implementation Rules

- **Named exports only** — Use `export { ComponentName }`. No `export default`. This ensures consistent imports and simplifies refactoring.
- **Typed props** — Define explicit TypeScript interfaces for all props. Co-locate types at the top of the component file or in a `ComponentName.types.ts` file for complex types. Never use `any` for props.
- **Sensible defaults** — Provide default values for optional props where a reasonable default exists.
- **Functional components only** — Never write class components. All new components must be functional.

```typescript
// ✅ Correct
interface StatusBadgeProps {
  status: 'active' | 'inactive' | 'pending';
  size?: 'sm' | 'md' | 'lg';
}

export function StatusBadge({ status, size = 'md' }: StatusBadgeProps) { ... }

// ❌ Wrong — default export, untyped props
export default function StatusBadge(props) { ... }
```

## Three UI States

Every component that depends on async data **must** handle three states:

1. **Loading** — Show a skeleton, spinner, or progress indicator. Never leave the screen blank.
2. **Error** — Display a meaningful message with a recovery action (e.g., retry button). Never show raw error objects to the user.
3. **Empty** — Show a helpful message when the data set is empty (e.g., "No risks found. Create your first risk.").

Use the App Router file conventions (`loading.tsx`, `error.tsx`, `not-found.tsx`) at the route level. For component-level states, handle them explicitly inside the component using TanStack Query's `isLoading`, `isError`, `data` states.

## State Management

| State type   | When to use                 | Implementation                                       |
| ------------ | --------------------------- | ---------------------------------------------------- |
| Local        | UI-only, single component   | `useState`, `useReducer`                             |
| Lifted       | Shared between 2–3 siblings | Parent `useState` + pass down via props              |
| Context      | Deeply nested consumption   | `createContext` + `useContext` (theme, locale, auth) |
| Server cache | Remote data with caching    | TanStack Query (`useQuery`, `useMutation`)           |

- **TanStack Query is the server-state manager** — never store API responses in React state or context. Use `useQuery` for reads and `useMutation` for writes.
- Use `useReducer` over `useState` when state transitions are complex (multiple related values, action-based updates).
- Avoid prop drilling beyond 2–3 levels — use context or composition (slots/children) instead.
- This project does **not** use a global client-state store (no Redux, Zustand, Jotai). If you think you need one, discuss it first.

## Server Components vs Client Components

- All components are **Server Components by default** in the App Router. Add `'use client'` only when you need:
  - Browser APIs (`window`, `document`, `localStorage`)
  - Event handlers (`onClick`, `onChange`, `onSubmit`)
  - React hooks (`useState`, `useEffect`, `useContext`, `useReducer`)
  - TanStack Query hooks
  - Third-party client libraries (e.g., `sonner`, `next-themes`)
- **Push `'use client'` to the leaves** — keep layouts and parent components as Server Components. Create small Client Component wrappers for interactive parts.
- Never add `'use client'` to a layout unless absolutely necessary. Wrap the interactive portion in a separate Client Component instead.
- Server Components can `import` Client Components, but **not** the other way around. Pass Server Component content to Client Components via `children` or slot props.

## Error Handling

- Use the App Router's `error.tsx` file convention for route-level error boundaries.
- For component-level error handling, wrap data-dependent sections with a React error boundary component.
- **Per-feature boundaries are better than one global boundary** — a failing chart should not take down the entire dashboard.
- Error boundaries do **not** catch errors in event handlers, async code, or server-side rendering — handle those with `try/catch`.
- Always provide a recovery action in error states (retry button, link to reload).

## Performance

| Technique             | API                                     | When to use                                        |
| --------------------- | --------------------------------------- | -------------------------------------------------- |
| Component memoization | `React.memo(Component)`                 | Prevent re-render when props are unchanged         |
| Expensive computation | `useMemo(() => compute(data), [data])`  | Heavy calculations derived from state/props        |
| Stable callbacks      | `useCallback(fn, [deps])`               | Callbacks passed to memoized children              |
| Dynamic import        | `next/dynamic` with `{ ssr: false }`    | Heavy client-only libs that depend on browser APIs |
| Streaming             | `<Suspense>` boundaries + `loading.tsx` | Progressive page loading, avoiding layout shift    |

- **Do not memoize by default.** Measure first. `React.memo` only helps when re-renders are measurably expensive and props don't change often.
- **Route-level code splitting is automatic** in the App Router — each `page.tsx` is a separate chunk. You do not need to manually split routes.
- Use `next/dynamic` with `{ ssr: false }` only for heavy client-only components that depend on browser APIs (e.g., chart libraries using `window` or `canvas`). Do not use `React.lazy()` in Server Components — it is unsupported there. In Client Components, `React.lazy()` with `<Suspense>` is valid for code-splitting, but prefer `next/dynamic` for App Router compatibility.
- Prefer `loading.tsx` file convention and `<Suspense>` boundaries for streaming and progressive loading.

## React Anti-Patterns

| Anti-Pattern                                  | Why it's wrong                           | Fix                                                      |
| --------------------------------------------- | ---------------------------------------- | -------------------------------------------------------- |
| Inline `{}` / `[]` as props to memoized child | New reference every render defeats memo  | Lift to module-level constant or `useMemo`               |
| Missing or wrong dependency array             | Stale closures, infinite loops           | Include all reactive values; lint with `exhaustive-deps` |
| `useEffect` for derived state                 | Unnecessary extra render cycle           | Compute during render: `const x = fn(props.y)`           |
| Index as list key                             | Breaks reconciliation on reorder/delete  | Use a stable unique ID from data                         |
| Prop drilling through 4+ levels               | Fragile, hard to maintain                | Use context or composition (children/slots)              |
| Monolithic component (300+ lines)             | Hard to test, reuse, understand          | Split into composed sub-components                       |
| Duplicating an existing component             | Inconsistency, maintenance burden        | Extend existing with variants (CVA)                      |
| `export default`                              | Inconsistent imports, harder refactoring | Named exports: `export { Component }`                    |
| Hardcoded colors/spacing in JSX               | Breaks theming, inconsistent             | Use Tailwind classes / design tokens                     |
| Storing API data in `useState`                | Stale data, no caching, no dedup         | Use TanStack Query `useQuery`                            |

## Component Checklist

Before marking a component implementation as complete:

- [ ] Single responsibility — one clear purpose
- [ ] Typed props — explicit TypeScript interface, sensible defaults
- [ ] Named export — no `export default`
- [ ] Design tokens — no hardcoded visual values
- [ ] Loading state — skeleton or spinner for async data
- [ ] Error state — meaningful message with recovery action
- [ ] Empty state — helpful message when no data
- [ ] Composition — uses `children`/slots, not prop sprawl
- [ ] `'use client'` only where required — pushed to leaf components
- [ ] Tailwind classes via `cn()` / `twMerge` for conditional styling
- [ ] Accessible — proper ARIA attributes, keyboard navigable, focusable
